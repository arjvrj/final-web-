## 2. How the rewrite was done

The page is generated by a script so that the change is auditable and repeatable:

1. Read the original file from **git** (`stage-3-start`), not from disk.
2. Keep the PHP block **byte for byte**. Verified:
   `PHP block: original 12,179 → new 12,403 chars; differing lines: 16` — all 16
   are the 404 branch's `<head>`/`<body>` (Tailwind → design classes).
3. Extract the original inline JavaScript and apply **16 presentation-only edits**
   with a hard assertion on each (`exactly one match, or abort`). Every AJAX call,
   every state variable, the clipboard logic, the expiry guard and the validation
   are unchanged.
4. Emit the new markup and the patched script.

### The 16 JS edits (presentation only)

1. chip deselect — inline violet style → `.selected` class
2. chip select — inline violet style → `.selected` class
3. chip reset after a rating change — inline style → class removal
4. generate button — Font Awesome spinner → design `.spinner`
5. regenerate label — icon → `↻ Regenerate reviews`
6. generate label — icon → `Write my reviews →`
7. stars fill in on tap — `☆` → `★` before the block slides away *(added)*
8. Google button — FA spinner → `.spinner`
9. Google button label — icon → `Review us on Google →`
10. feedback button — FA spinner → `.spinner`
11. feedback button label — icon → `Send feedback →` (2 occurrences)
12. selected-keyword tags — Tailwind pill → design `.chip`
13. draft cards — Tailwind markup → design `.review-card` (radio, title, word count, textarea, copy link)
14. empty drafts message — Tailwind → `.small-note`

## 6. Design details NOT reproduced, and why

1. **"Add your own details" textarea (0/1000 counter) and "Anything else?" disclosure**
   — the design sends these to the AI. This app has no field for them and the
   generator only accepts slugs and keywords, so adding them would be a fake input
   that silently throws the customer's words away. Left out.
2. **"I confirm this reflects my actual experience" checkbox** — the app's flow has
   no confirmation step; the customer picks a draft and copies it. Adding a
   mandatory checkbox would change the behaviour this stage has to preserve. Left out.
3. **One "Copy review" button + "Copy & continue to Google"** — the app copies per
   draft (each copy also records the review via `?action=submit`). Kept per draft,
   drawn as the design's `.link-button`.
4. **Editable drafts** — the design lets the customer edit a draft before copying.
   The app copies `aiReviews[index]`, not what is in the textarea, so an editable
   box would ignore the customer's edits. The textarea stays `readonly`.
5. **Draft 1 pre-selected** — the design starts with the first draft chosen; the app
   deliberately waits for an explicit tap before enabling the Google button. Kept
   the app's rule; the *selected styling* is compared 1:1 in §4.
6. **Stars stay visible with "4 stars selected"** — the app hides the rating block
   after a tap (`hideRatingBlock()`); the note is only visible at rest.
7. **Test / development banner** — the app has no test mode, so `.environment` is
   used for the expired state only.
8. **Language row, "Anonymous activity counts" note** — no backend for either.
9. **Brand box stays on screen during the drafts step** — the design swaps the whole
   view; keeping the business name visible is clearer on a real page.
10. **Per-card theme colour** — the app let each card tint the page. The design has
    one violet customer identity (locked palette decision), so the page now uses the
    design's colours. `themeColors` is still passed to the page; nothing reads it
    for styling any more.

One behaviour was **improved** rather than reproduced: the page-level Google link
(`.direct`) is only rendered when the card actually has a Google review URL. The old
fallback pointed at `https://www.google.com/search?q=review`, which is not the
business's page; when no URL is set the design's own
`.direct.unavailable` note is shown instead.
